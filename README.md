# Research Agent Skills

一套可组合的科研工作流技能，覆盖：

```text
研究想法 → 实验验证 → 论文写作
```

仓库中的三个技能可以独立使用，也可以通过 `research_state/`（研究状态目录）和共享数据协议组成完整闭环。

## 为什么要做这个项目？

这个项目的初衷不是把每个人都训练成高产论文作者，而是把论文生产中最消耗精力、最容易被环境阻塞的部分交给 AI托管，让研究者把时间放回找实习、找工作或自己真正想推进的方向。

对于不想把大量时间花在读论文、组织实验和反复写作上的人，或者处在指导不稳定、资源有限、组内难以持续产出论文的环境中的人，论文往往更像一个带有不确定性的研究抽卡过程：

```text
提出一个有潜力的 idea
  → 用最低成本验证
  → 根据结果决定继续、修改、暂停或放弃
  → 将真实证据整理成论文
```

这里的“抽卡”不是放弃科学标准，而是承认论文结果受到想法质量、实验资源、时间、审稿偏好和偶然性的共同影响。这个项目试图把不可避免的不确定性变成可记录、可比较、可复盘的流程。

它尤其适合：

- 想专注实习或工程工作，只希望用较少精力维持一条可靠研究线的人；
- 缺少稳定导师指导，需要自己完成问题定义、实验验证和论文组织的人；
- 不想每次从零开始读大量论文，希望 AI 先完成领域扫描和候选 idea 筛选的人；
- 愿意把自己的研究判断、领域经验和失败经验加入系统的人。

这个项目不会制造论文、伪造创新或包装不存在的实验结果。它的目标是减少重复劳动，而不是降低证据要求。

## 技能

| 技能 | 负责内容 | 可独立使用 |
|---|---|---|
| `research-idea-lab` | 探索想法、基线改造、持续迭代、文献监控、目标领域新颖性核查和实验前对齐 | 是 |
| `research-experiment-lab` | 低成本验证、正式实验、方法身份隔离、机制实现检查、运行调试、统计和证据验证 | 是 |
| `ai-research-writing-skill` | 论文故事、论断—证据、范例卡、章节、引用、图表和投稿检查 | 是 |

论文绘图不包含在本仓库中，请使用独立仓库 [paper-figures-skill](https://github.com/threeing3/paper-figures-skill)。

## 当前版本更新总览

本轮改造的核心不是增加更多检查，而是把检查放到正确阶段：探索时保留可能性，验证时确认机制真的实现，正式实验时隔离方法身份，写作时只使用与主张匹配的证据。

### 1. 探索与严格审查彻底分离

- 模糊的“找方向”“继续想”“救方向”默认进入探索，不再自动触发评分、审稿人攻击、致命门槛或拒绝。
- 一次标准探索优先返回 3–5 个实质不同的候选；证据不足时仍返回可用种子、缺失信息和救援路线，不能只输出“没有合格想法”。
- 完整评分、排序、投入决策和放弃决策只有在使用者明确要求时才运行。
- `quick`（快速深度）与 `standard`（标准深度）只决定检查量和输出长度，不改变研究阶段的权限。

### 2. 支持不完善想法和持续迭代

- 想法成熟度分为 `seed`（想法种子）、`developing`（发展中方案）和 `validation-ready`（可验证方案）。
- 一次实验没有效果时，先判断问题假设、机制、实现和测量中的哪一层失败，不自动丢弃整个方向。
- 修复代码、配置、接口或未启用问题只递增实现修订；机制实质变化才递增想法修订；核心失败解释或解决原理改变时建立有关联的派生想法。
- 不设置机械的科研总迭代次数，但新一轮运行必须具有新证据、实质改动或有依据的实现修复。

### 3. 正式支持基线改造和机制组合

- 候选类型覆盖机制发明、基线改造、机制组合、跨领域迁移以及简化或诊断型创新。
- 已知可信基线时，候选组合中至少包含一个可执行的基线改造或机制组合方案。
- 基线改造必须说明准确版本、目标失败、增加/替换/移除/重连/组合位置、改动前后流程、复用和重设计部分、资源变化及必要消融。
- “加一个模块”不再被当作完整方案；必须解释模块为何解决特定失败，以及什么对比能够隔离它的真实作用。

### 4. 新颖性按目标领域的完整机制判断

- 机制发现可以使用任何领域和会议范围内的高质量一手来源。
- 新颖性核对检查目标领域内所有可信来源，不用指定会议列表人为缩小范围；会议列表只用于审稿模式和投稿标准校准。
- 相邻领域已有原理、目标领域已有单个组件或多篇工作分别包含不同零件，不自动占据目标领域新颖性。
- 只有目标领域已有工作实现等价的完整运行机制，才判定为 `occupied`（已被占据）。
- 聚焦审查使用 `supported`（当前检索支持）、`occupied` 或 `uncertain`（证据不足）三态，并分别报告思想来源、迁移价值、贡献强度和实验成熟度。

### 5. 增加使用者批准的低成本验证通道

- 正式新颖性审查前可以先运行 `exploratory-validation`（探索性验证），避免因为新颖性仍不确定就过早放弃可能有效的机制。
- 每轮启动前必须向使用者展示想法、基线改动、验证问题、成功/失败/无法判断的含义、停止条件、时间、成本和日志位置。
- 默认单轮范围不超过 100 元和 24 小时；超出范围或进入新一轮科学验证时必须重新确认。
- 同一轮已批准范围内的预声明任务不重复询问，普通只读检查和技能内部交接也不制造额外交互。

### 6. 强制检查程序是否真正实现并启用了想法

- 负面指标不能直接解释为机制失败，必须先取得 Activation evidence（激活证据，证明模块确实执行并影响后续计算）和 Intervention evidence（干预证据，通过关闭、打乱或替换确认效果来源）。
- 结果区分为实现未确认、测量无法判断、机制反证和支持性信号。
- 只有机制已经正确实现、实际启用且测量能够区分解释时，负结果才可以更新机制判断。

### 7. 隔离完整方法与开发版本

- 实验计划将方法标记为 `full`（完整方法）、`simplified`（简化方法）、`proxy`（代理方法）、`toy`（玩具方法）或 `debug`（调试方法）。
- 简化、代理、玩具和调试版本可以用于诊断，但不能进入最终论文方法描述、正式结果表或核心比较。
- 只有写明完整科学配置且明确允许论文使用的完整方法，才能升级为 `paper-ready`（论文可用证据）。

### 8. 增加持续文献监控

- 稳定想法可以按时间窗口增量扫描新论文，不必每次从头执行完整检索。
- 监控结果使用 `RELAX`（暂时无实质重叠）、`RESEARCH`（需要深入调查）和 `FOLLOW-UP`（需要立即跟进）三种行动信号。
- 重叠分别按问题、机制、证据、基准、主张和投稿定位记录。
- 监控只能更新检索信心、触发精读、差异化发展或主张修订，不能直接拒绝想法，也不能代替正式新颖性审查。

### 9. 加入去防御化质量控制

- 发布相关产物前将内容分为 `remove`（删除多余防御内容）、`keep`（保留科学必要信息）和 `warn-only`（仅警告，等待使用者判断）。
- 内部批准、门槛通过、版本确认等流程语言不能进入论文正文；论文只描述实际方法、配置、数据和协议。
- 删除重复冒烟测试、低概率情形堆叠、无作用的流程叙述和普通本地交接中的冗余哈希。
- 远程下载、不可变代码快照、官方模板包和外部系统明确要求的完整性校验仍然保留。

### 10. 强化论断—证据与文件所有权

- Claim–Evidence Matrix（论断—证据矩阵）现在记录所需证据、当前证据、准确想法/实验修订、支持状态、限制和下一步行动。
- 支持 `overstated`（表述过强）和 `unclear`（无法判断），不能通过编造内容自动修复缺失证据。
- 写作技能可以从使用者提供或批准的优秀论文中提取 Exemplar card（范例卡，保存可迁移的叙事和证据组织结构），但禁止复制具体技术内容或措辞。
- 三个技能遵循“广泛读取、窄范围写入”：想法技能拥有想法和新颖性状态，实验技能拥有计划、运行、日志和验证，写作技能拥有论文正文和论文级论断—证据矩阵。
- 审查和审计默认只提出修改建议，除非使用者明确授权直接修改对应技能拥有的文件。

### 11. 状态兼容与验证结果

- 一致性报告统一使用 `research_state/ideas/state_consistency.json`；读取器继续兼容旧文件名，但不自动删除历史文件。
- 新本地交接优先使用稳定 ID（标识符）、修订号、项目相对路径、时间和 Git（版本控制）提交，不再强制生成通用文件哈希。
- 历史契约通过 `active`（有效）、`invalidated`（已失效）或 `superseded`（已替代）生命周期保留，不批量重写科学内容。
- 当前版本通过 102 项自动测试：想法技能 26 项、实验技能 39 项、写作技能 37 项；仓库包含 8 个共享 Schema（数据结构约束）和 5 个写作技能内部 Schema，测试过程中没有删除本地文件。

## Idea Skill 的分阶段逻辑

`research-idea-lab`（研究想法技能）默认先寻找和发展可能性，不会在候选刚出现时启动完整审稿、致命门槛或数值打分。完整评分只在使用者明确要求严格评审、排序、投入决策或放弃决策时运行。

标准流程是：

```text
探索种子与基线改造候选
  → 轻量目标领域查重
  → 持续完善问题、机制和实现版本
  → 使用者查看对齐卡并批准低成本验证
  → 检查程序是否真的实现并启用了设想机制
  → 有潜力后做严格目标领域新颖性核查
  → 再决定是否进入完整实验和论文主张
```

想法成熟度分成 `seed`（想法种子）、`developing`（发展中方案）和 `validation-ready`（可验证方案）。种子只需说明具体问题和可能的解决办法；不完整不等于失败，也不会被写成拒绝。每次有明确基线时，3–5 个返回候选中至少包含一个可定位的基线增改或机制组合方向。

严格新颖性核查只给出三种结论：`supported`（现有检索支持目标领域新颖）、`occupied`（目标领域完整等价机制已被占据）或 `uncertain`（证据仍不足）。来源领域已有原理只用于说明思想来源；只有目标领域已经实现完整等价机制，才占据目标领域新颖性。贡献强度、迁移适配价值和实验成熟度分别判断，不能被改写成“不新颖”。

### 1. 完整严格评审才使用致命门槛

当使用者明确要求完整严格评审时，以下任一问题为 `fail`（失败）或 `unresolved`（未解决），想法就不能进入正式 `experiment-ready`（可实验状态）：

- 核心贡献已经被近似工作完整占据；
- 没有实验能够区分声称的机制和数据、算力、模型规模或提示词差异；
- 一个明显的简单基线或公平计算预算基线就能消除收益；
- 所需数据、算力或评估条件不可获得；
- 核心结论依赖数据泄漏、无效测量或不合适的数据使用；
- 贡献类型与准备声称的论文结论不匹配。

### 2. 按需评估 11 个维度

每个维度使用 0–4 分，并附带证据和置信度。总分不是概率，也不是录用率预测。

| 维度 | 关注的问题 |
|---|---|
| 问题重要性 | 问题是否真实且有影响？ |
| 问题半衰期 | 项目完成前问题是否仍然存在？ |
| 机制清晰度 | 是否说明了为什么会有效？ |
| 新颖性证据 | 检索是否充分，差异是否清楚？ |
| 抗碰撞性 | 明天出现近似论文后，是否仍有独立价值？ |
| 科学可靠性 | 假设是否自洽且可证伪？ |
| 兴奋度/意义 | 如果成立，是否带来能力、理解或实践变化？ |
| 可测试性 | 是否存在低成本的区分性验证？ |
| 评估完整性 | 是否有直接指标、强基线、泛化和失败分析？ |
| 可行性 | 数据、算力、时间和工程条件是否允许？ |
| 失败后的剩余价值 | 失败后是否仍能留下方法、资源或分析？ |

其中 `soundness`（科学可靠性）和 `excitement`（研究意义）必须分开记录：一个 idea 可能可靠但不重要，也可能很吸引人但无法验证。

### 3. 用信息增益选择验证

系统不优先选择最复杂或最容易跑出好数字的实验，而是选择单位时间和算力下最能区分竞争性解释的 pilot（先导实验）：

- 如果机制成立，会看到什么？
- 如果只是模型变大、数据变多或提示词更好，会看到什么？
- 哪个最小实验能把这些解释区分开？
- 每种结果会让 idea 继续、修改、暂停还是放弃？

量化结果服务于实验决策，不制造虚假的精确感。

### 4. 正式升级前检查“背景—动机—方法”链条

一个想法要升级为完整实验和论文核心贡献，不能只有一个漂亮的方法名称。必须先写清楚：

```text
背景：现实中存在什么问题？
  ↓
动机：现有方法在哪个具体场景失败，为什么需要改变？
  ↓
方法：提出的机制如何直接解决这个失败，如何被实验证伪？
```

分别给背景扎实度、动机必要性、方法对齐度和方法新颖性打 0–4 分，再给三条连接打分：`背景→动机`、`动机→方法`、`方法→评估`。

```text
base = 0.20*背景 + 0.25*动机 + 0.25*方法对齐 + 0.15*方法新颖性 + 0.15*评估匹配
coherence = min(背景→动机, 动机→方法, 方法→评估)
idea_readiness = 0.70*base + 0.30*coherence
```

这些分数只服务于使用者明确请求的完整严格评审，不阻止已经对齐的低成本探索性验证。任何分项或连接低于 2 分，都不能进入完整 `experiment-ready`（可实验状态）；2.5–3.2 可以继续做有明确停止条件的探索性验证；达到 3.2 且所有链条至少为 3 分、适用门槛通过后，才适合按完整评审路径升级。

这个公式故意保留最低连接分：方法再漂亮，也不能弥补虚构的背景；动机再强，也不能弥补方法与评估不匹配。

## Idea Skill 的产出逻辑

Idea Skill 的产出不是一串未经筛选的灵感，而是逐步收敛的研究状态：

```text
领域扫描
  → 3–5 个不同成熟度与不同类型的候选
  → 轻量目标领域查重和救援路线
  → 选中方向的机制与基线改动蓝图
  → validation-alignment.yaml
  → 用户明确批准低成本验证
  → 严格目标领域新颖性三态核查
  → 可选的完整评分与审稿人攻击
  → 用户选择正式升级
  → idea_contract.yaml
```

候选可以从不完整种子开始。进入验证前必须留下：问题假设、机制假设、基线及准确改动位置、实现版本、最强替代解释、机制启用证据、关闭或打乱机制后的干预证据、三类结果解释、停止条件、成本时间以及使用者批准。实验效果不好时，先区分实现未生效、测量无法区分和机制受到反证；只允许最后一种直接更新机制判断。

使用者可以加入自己的领域见解，例如某类工作在自己的方向中通常不被认可、某个指标容易被质疑、某个基线实际上更强。这些见解应作为带来源和置信度的评估规则加入，而不是直接覆盖论文事实。这样系统会逐渐形成个人化的 idea 评估标准，同时保留可审计的证据链。

## Experiment Skill 的设计逻辑

`research-experiment-lab` 的定位不是“让 AI 多跑几个实验”，而是把一个已经选中的研究想法，转换成边界清楚、过程可审计、结论可复核的证据。它遵循一条单向证据链：

```text
validation-alignment.yaml → 低成本探索性验证

idea_contract.yaml → state_consistency.json → 正式 experiment_plan.json → 不可变 run → verification_report.json → research_handoff.json
```

新增的质量控制层会在论文和正式实验产物前清理防御性流程语言、重复测试与无意义本地哈希。跨阶段身份以 ID、修订号、项目相对路径和方法配置为主；远程下载、不可变快照和官方模板校验仍保留必要摘要。

稳定想法可以使用持续文献监控，按时间窗口输出 `RELAX`、`RESEARCH` 或 `FOLLOW-UP`，用于更新检索信心、触发精读或要求修改主张，但监控结果本身不能直接拒绝想法。正式实验还必须声明方法层级；简化、代理、玩具或调试实现不能进入论文级结果。

具体设计分成五层：

1. **双入口**：低成本探索性验证绑定使用者批准的 `validation-alignment.yaml`（验证对齐卡），不要求完整想法契约；正式实验才绑定 `idea_contract.yaml`（想法契约）和通过的目标领域新颖性状态。
2. **预注册与冻结**：执行前固定假设、对比方法、数据集与划分、指标、随机种子、成功/失败阈值、停止条件、预算和潜在混杂因素，避免看到结果后再改规则。
3. **不可变执行**：每次运行生成新的 `run_id`（运行标识），正式运行不原地覆盖；同时保存可读日志、结构化指标、资源占用、环境、代码同步状态和输出清单。
4. **最小区分性调试**：失败时先确认程序是否真的实现并启用了设想机制，再区分实现、测量与机制问题；一次只改一个因素并新建运行。连续三次相同技术修复仍失败就暂停讨论，但不对科研想法设置机械的总迭代次数。
5. **科学验证**：`completed-technical`（技术完成）不等于 `verified-scientific`（科学验证完成）。探索性验证最多到 `verified-diagnostic`（诊断证据已核验），不能直接进入论文；只有正式计划通过种子、基线公平性、数据划分、指标可重算性、不确定性和机制证据检查后，才标记为 `paper-ready`（可进入论文）。

实验模式按成本和目的拆开：`pilot`（低成本试跑）用于发现配置级错误，`full`（主实验）回答核心假设，`ablation`（消融）拆解贡献，`robustness`（稳健性）和 `efficiency`（效率）验证边界，`reproduction`（复现）确认外部结果，`debug`（调试）定位故障。实验输出的是证据和 `experiment_request.json`（实验请求），可以触发想法修订，但不会偷偷改写 Idea Skill 的原始契约。

## Writing Skill 的来源与适配

本仓库中的 `ai-research-writing-skill`（AI 研究写作技能）是基于上游仓库 [jin-s13/ai-research-writing-skill](https://github.com/jin-s13/ai-research-writing-skill) 的本地适配版本，不把它重新宣称为原创项目。上游 README 和其 schema（结构定义文件）中的 `$id` 都明确指向该仓库。

本仓库保留上游的核心写作约束：先建立 claim-evidence map（论断—证据映射），禁止编造引用、数字和实验结论，生成 LaTeX/BibTeX（论文排版与参考文献格式）及编译检查产物，并把人的判断保留在关键决策环节。在此基础上做了三类适配：

- 对接本仓库的 `research_state.json`、`idea_contract.yaml`、`state_consistency.json`、`experiment_plan.json`、`verification_report.json` 和 `research_handoff.json`，让想法、实验和论文共享同一套状态、生命周期与证据边界。
- 对实验缺口只生成结构化的 `experiment_request.json`（实验请求），交回 `research-experiment-lab` 执行；写作技能本身不设计、启动或调试实验，避免把推测写成结果。
- 将论文图表工作指向独立仓库 [paper-figures-skill](https://github.com/threeing3/paper-figures-skill)，写作技能负责 claim、caption（图注）、LaTeX 引用和证据绑定，不把绘图工具重复打包进来。

因此，三者的职责边界是：Idea Skill 负责选择“值得验证什么”，Experiment Skill 负责产生“能否支持它的证据”，Writing Skill 负责把“已经验证的证据”组织成可检查的论文叙事。

## 共享协议

跨技能文件统一保存在项目根目录：

```text
research_state.json
research_state/
├── ideas/<idea-id>/idea_contract.yaml
├── ideas/idea_pool.json
├── ideas/state_consistency.json
├── ideas/<idea-id>/validation/<alignment-id>.yaml
├── ideas/<idea-id>/literature_monitor/<monitor-id>.json
├── experiments/<experiment-id>/experiment_plan.json
├── experiments/<experiment-id>/verification_report.json
└── paper/claim_evidence.json
```

标准流转为：

```text
validation-alignment.yaml
  → exploratory-validation experiment_plan.json
  → verified-diagnostic

idea_contract.yaml
  → state_consistency.json
  → formal experiment_plan.json
  → paper-ready verification_report.json
  → research_handoff.json
  → paper_state.json
```

详细规则见 [`docs/shared-protocol.md`](docs/shared-protocol.md)，数据结构见 [`schemas/`](schemas)。

## 设计原则

- 三个技能通过文件协议连接，不通过隐式上下文连接。
- 每个技能只写自己拥有的状态目录。
- 想法机制发生实质变化时，实验计划必须失效并重新确认。
- 写作技能可以提出实验请求，但不能直接启动实验。
- 实验技能可以提出想法修订请求，但不能直接修改想法契约。
- 负结果、失败运行、缺失证据和阻塞项必须保留。
- 不允许把未验证结果写成论文结论。

## 安装

安装单个技能：

```powershell
python install-skill-from-github.py `
  --repo threeing3/research-agent-skills `
  --path skills/research-idea-lab
```

将路径替换为 `skills/research-experiment-lab` 或 `skills/ai-research-writing-skill` 即可安装其他技能。完整科研闭环需要安装三个技能。

## 诚实边界

这个项目可以减少读论文、搭故事和整理材料的负担，但不能保证 idea 新颖、实验成功或论文接收。它把论文看作一个需要管理不确定性的研究过程，而不是承诺结果的自动售货机。

## 兼容性

技能使用通用 `SKILL.md`（技能说明文件）格式，优先面向 Codex，也可迁移到其他支持 Agent Skills 的编程代理。
